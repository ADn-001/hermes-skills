Regenerate the DAILY report file from the raw activity logs. Do exactly this, then stop.

Before first use, replace the two placeholders:
  <REPORTS_DIR>   the directory holding the daily log files (YYYY-MM-DD.md)
  <WRITE_CMD>     the command that writes the report file, reading the body from stdin

1. Read today's log file in <REPORTS_DIR> (the newest YYYY-MM-DD.md). If there is no
   file at all, do nothing and say "no activity logged" — do not create one.
2. Write a considered, genuinely useful daily report and save it with:

     <WRITE_CMD>

   That command reads the report body from stdin and writes the file that the assistant
   serves when the user asks for a report — so this job IS the report.

   If that command is unavailable, write the report file directly in the same shape:

     # Daily report — <the date the log covers>

     ## Status
     - <project>: <phase N of M, test state>. Named projects, not prose.

     ## Needs you
     - <anything requiring a decision: an unapproved finding id, a blocked phase, a failure>

     ## Done today
     - <what landed>

Content rules:
- This is a STATUS channel for the user's codebases and assigned work. Ignore routine
  background operations entirely — routine chatter is not what this report is for, and
  the log is full of it.
- Name concrete projects, phases and finding ids (e.g. CR-my-project-0014). A report that
  says "several things happened" has failed.
- If nothing needs the user's attention, omit the "Needs you" section rather than writing
  "nothing". If there was no activity at all, say so in one line.
- Do NOT log this run to the daily log file. Writing the report is the whole job, and a
  self-referential entry would make the report immediately look stale.
- Do not commit anything to git. Do not modify any other file.

Your final response: the file path you wrote and the date it covers, in one line.
